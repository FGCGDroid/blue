# 蓝队报告

## 原则
- 只写库里有的：`blue_report` 从事实库生成，手写报告必须与库一致。
- 区分“已证实 / 高度可能 / 线索”，不要把推测写成事实。
- 每条结论可复现：目标 → 证据 → 命令/请求 → 时间 → 影响。
- 敏感数据打码；凭据不写明文，写存放位置与轮换状态。

## 结构
1. **摘要**：防守目标、时间范围、核心结论（是否失守、丢了什么、是否恢复）。
2. **态势**：资产数、告警数、发现数、IOC 数、任务完成率。
3. **事件时间线**：UTC 时间、主体、动作、对象、证据来源。
4. **失陷与影响**：Flag/服务/数据/主机，影响面与持续时间。
5. **处置**：隔离、清除、恢复、验证；每步结果。
6. **根因**：入口、暴露面、检测缺口。
7. **整改**：已修复、待修复、风险接受人、截止时间。
8. **附录**：IOC 清单、证据哈希、命令输出、检测规则。

## 证据标准
- 日志：文件路径 + 行号/时间 + 原文片段。
- 流量：pcap 文件 + 五元组 + 帧号。
- 主机：命令 + 输出 + 文件哈希。
- 样本：SHA-256 + 来源 + 分析结论。
- 账号：登录时间、来源、成功/失败、权限变更。

## 写作口径
- 先结论后细节；一页能看懂，附录能复现。
- 不堆砌无关 IOC；只留与本场相关的。
- 失败也要写：查过什么、为什么没查到、缺口在哪。
- 修复项写清“改了什么、怎么验证、怎么回滚”。

## 交付
`blue_report write=true` 输出 Markdown 到 `$DSH_HOME/blue/reports/`，再把路径给用户。
比赛现场可另存 PDF/HTML，但事实以库为准。
