# 3.0 / 4.0 顺序

> 决策：2026-11-17  
> 结论：**3.0 先发布，4.0 后开发；4.0 长线测试期间，3.0 是回退基线。**

## 用户原始想法

```text
先把 V3.0 搞好
然后搞 4.0
最后 3.0 发布
4.0 长线测试
```

## 调整后的顺序

只改一处：**3.0 发布放到 4.0 开发之前**。

```text
1. 3.0 搞好：M4 工具 + M5 控制台 + 影子双跑
2. 3.0.0 发布
3. 3.0 真实使用 / 影子 soak
4. 从 3.0 稳定 tag 切 4.0-dev
5. 4.0 开发
6. 4.0 长线测试（3.0 作为回退）
7. 4.0 发布
```

## 时间表

```text
2027-08        3.0.0 发布
2027-09 ~ 12   3.0 真实使用；M5 控制台并行
2028-01        3.1.0 发布
2028-Q1        4.0 立项/技术验证（从 v3.0.0 切 4.0-dev）
2028-Q2 ~ Q3   4.0 开发
2028-Q4        4.0 功能完成 / 4.0-rc
2029-Q1 ~ Q2   4.0 长线测试（至少 6 个月）
2029-Q3        4.0 发布
```

3.0.0 先发，不因控制台或 4.0 推迟。  
3.1.0 只做控制台，不改内核契约。

## 为什么不是“4.0 写完再发 3.0”

```text
3.0 会被 4.0 的复杂度拖住
4.0 会建在没发布、没真实使用的 3.0 上
出问题时分不清是 3.0 的坑还是 4.0 的坑
没有稳定回退版本
```

先发 3.0 的收益：

```text
真实流量先打 3.0
3.0 成为 4.0 的回退基线
4.0 可以放心改架构
3.0 的 P0 修复继续进 3.0 维护线
```

## 分支策略

```text
main        2.0 维护线（只 P0/安全/DSH 兼容）
3.0-dev     3.0 开发线
4.0-dev     4.0 开发线，从 v3.0.0 tag 切出
v3.0.0      3.0 发布 tag
v3.1.0      控制台发布 tag
v4.0.0      4.0 发布 tag
```

规则：

```text
4.0 不合并进 3.0
3.0 只修 P0/安全/兼容，不加新功能
4.0 依赖 3.0 的契约，但不依赖 3.0 的未发布改动
4.0 必须能和 3.0 并行安装/切换
```

## 4.0 长线测试门槛

```text
至少 6 个月，或 3 次真实授权演练
3.0 回退演练至少 1 次
无未关闭 P0
K1–K5 在 4.0 上重新取证
```

长线测试期间：

```text
3.0 继续维护，不冻结
4.0 只修测试发现的问题
4.0 不因为“快测完了”提前发布
```

## 出口

```text
3.0.0 发布：2027-08
3.1.0 发布：2028-01
4.0-rc：2028-Q4
4.0 发布：2029-Q3（长线测试后）
```

这不是承诺，是顺序约定。  
**3.0 没发布，4.0 不开发。**
