# 3.0 架构决策记录

> 只记录已经定下的决定。  
> 状态：`accepted` 表示当前按此执行；`proposed` 表示待验证。

## ADR-001 全量重写实现，保留行为契约

```text
状态：accepted
日期：2026-11-17
```

**背景**

2.0 的四处结构债（tools 2609 行、client 1797 行、store 1384 行、网关 335 行）互相依赖，渐进式拆分会在很长时间里留下“半新半旧”的两套路径。

**决定**

3.0 重写 `domain / app / infra / tools` 四层实现；工具名、参数、返回、错误码、状态机、数据语义保持不变。

**理由**

- 路径阻断需要“先判定后读 body”，这不是在旧网关上能干净补出来的。
- 依赖方向需要一次性建立，否则旧代码会不断把 infra 拉进 domain。
- 行为契约保留，重写才不是第二个项目。

**代价**

- 需要 parity 基线，前期投入高。
- 重写期间不能加新功能。

**替代方案**

渐进式重构：风险分散，但会长期维护两套路径；否决。

## ADR-002 同仓库双树，不另开仓库

```text
状态：accepted
日期：2026-11-17
```

**背景**

3.0 开发期 2.0 仍要维护；如果 3.0 直接在 `lib/` 重写，`main` 上任何 2.0 修复合入都会冲突。

**决定**

```text
lib/    2.0 维护线
v3/     3.0 开发线
```

同一个仓库、同一个包名、同一个 npm 包；切换时再改入口。

**理由**

- 2.0 修复可以直接合并进 `3.0-dev`，不冲突。
- issue、release、文档、CI 都不用分家。
- 3.0 发布时只换入口，不换包名。

**代价**

- 开发期两套目录并存，需要明确“只改一边”。
- 切换提交会比较大，但只发生一次。

## ADR-003 内核优先，控制台放到 3.1

```text
状态：accepted
日期：2026-11-17
```

**背景**

`client.js` 1797 行，占重写工作量约四分之一，但对防守正确性贡献最小。

**决定**

3.0.0 保留 2.0 控制台，只保证 Host API 兼容；控制台重写放 3.1.0。

**理由**

- 3.0 的核心价值是路径阻断和分层，不是 UI。
- 先发一个能用的 3.0，避免两年没有可发布版本。
- Host API 稳定后，UI 可以独立替换。

**代价**

- 3.0 的控制台仍是旧结构，视觉和数据流不统一。
- 3.1 还要再做一次联调。

## ADR-004 先判定后读 body，失败关闭

```text
状态：accepted
日期：2026-11-17
```

**背景**

2.0 的内联网关先读 body 再检查，路径用正则匹配；`jwt-none` 曾出现“检测到但请求仍被转发”。

**决定**

网关固定顺序：

```text
raw URL
  → 规范化
  → 策略判定
  → block / allow
  → 只有 allow 才读 body
```

解码失败、策略缺失、配置错误一律阻断。

**理由**

- 检测不等于阻断；判定必须在副作用之前。
- 规范化后的路径才能做前缀/精确匹配，正则容易被编码绕过。
- fail-closed 是防守工具的默认值。

**代价**

- 误阻断会增加，需要 canary 和灰度。
- 规范化必须严格，否则会出现“合法路径被拒”。

## ADR-005 3.0 开发期，2.0 冻结

```text
状态：accepted
日期：2026-11-17
```

**决定**

2.0 只接受：

```text
P0 缺陷
安全修复
DSH 兼容
数据迁移修复
```

不接受新工具、新页签、新架构、重构。

**理由**

- 单人 18 小时/周，维护一旦放开就会吃掉 3.0。
- 2.0 的功能已经够用，3.0 不是靠 2.0 加功能追上的。

**代价**

- 2.0 用户的新需求要等 3.1/3.2。
- 需要在 issue/PR 上明确拒绝。

## ADR-006 不设硬期限，设里程碑出口条件

```text
状态：accepted
日期：2026-11-17
```

**决定**

不承诺发布日期；每个里程碑以“出口条件”判定完成。超期只顺延，不砍测试、不涨范围。

**理由**

- 项目没有外部截止日期，硬日期只会逼着砍质量。
- 单人项目最大的风险是“永远在写、永远不发”，出口条件比日期更能防止这一点。

**代价**

- 需要自律，否则会无限打磨。
- 每 6 周必须做一次可演示的进度检查。

## ADR-007 零新增运行时依赖

```text
状态：accepted
日期：2026-11-17
```

**决定**

3.0 继续只使用 Node 内置模块和 DSH 已有能力；不引入新的运行时 npm 依赖。

**理由**

- 供应链风险是防守工具自身的攻击面。
- 2.0 已经做到零运行时依赖，3.0 不回退。
- 审计、签名、SQLite、HTTP 都能用内置能力完成。

**代价**

- 某些能力要自己写，例如路径规范化、模板、校验。
- 需要更多测试覆盖自写部分。

## ADR-008 数据迁移必须可回滚

```text
状态：accepted
日期：2026-11-17
```

**决定**

2.0 → 3.0 迁移前自动备份；迁移带版本门；失败可回滚；回滚脚本必须演练。

**理由**

- 数据是唯一不可重建的资产。
- 旧库样本可能比设计时更脏。

**代价**

- M2 多 1–2 周。
- 需要维护迁移与回滚两套脚本。

## ADR-009 不为了“干净”删旧模块

```text
状态：accepted
日期：2026-11-17
```

**决定**

旧模块只在对应 parity 全绿、且无调用方后才删除；删除单独提交。

**理由**

- 2.0 的很多行为是事故换来的，删快了会丢。
- 保留旧模块可以做影子对比。

**代价**

- 开发期目录会更杂。
- 需要定期清理，但不能提前清。

## ADR-010 网关独立进程与独立端口

```text
状态：accepted
日期：2026-11-17
```

**背景**

2.0 曾对与 DSH 同进程的目标做 2MB 压测，把 DSH 打崩。  
网关是唯一直接面对不可信请求的组件，不能和 DSH 共享生命周期。

**决定**

```text
网关独立进程，不嵌入 DSH
默认监听 127.0.0.1:8787，可配置
端口被占用时拒绝启动，不自动换端口
DSH Host 不自动拉起网关
网关与 DSH 不做同进程压测
网关不直接写 blue.db，决策日志写 JSONL
```

**理由**

- 网关崩溃不能带走 DSH。
- 独立进程可以单独重启、单独限流、单独观察。
- 固定端口便于上游和浏览器配置；“自动换端口”会造成静默误连。

**代价**

- 多一个进程和端口要运维。
- 用户必须显式启动网关。
- 端口冲突要人工处理，不能自动恢复。

## ADR-011 没有真实数据仍保留迁移

```text
状态：accepted
日期：2026-11-17
```

**背景**

作者没有真实 2.0 数据需要迁移；但 npm 上仍有 2.0 用户，升级路径是发布契约。

**决定**

```text
3.0 保留 2.0 -> 3.0 迁移与回滚
M2 用 3 个合成 2.0 fixture 演练
M2 估算从 4–6 周降到 3–4 周
```

**理由**

- 自己没有数据，不等于所有用户都没有。
- 合成 fixture 可以覆盖空库、正常库、缺 hash 旧库三类结构。
- 删掉迁移会让 3.0 变成“只能全新安装”，违背升级承诺。

**代价**

- M2 仍要 3–4 周。
- 合成 fixture 可能漏掉真实脏数据；发布说明必须要求升级前备份。

## ADR-012 3.0 是能力超集，不是等价重写

```text
状态：accepted
日期：2026-11-17
```

**背景**

初版设计把“66 个工具不变、17 张表不变、旧控制台可连”写成了主目标。  
按那个标准做出来，3.0 只是“结构更整齐的 2.0”，不是跨越。

**决定**

3.0 必须同时过两门：

```text
兼容门：现有 66 个工具、数据、审批、证据不退化
跨越门：K1-K5 必须落地
```

跨越门：

```text
K1 真阻断
K2 策略可测试
K3 受控响应可执行
K4 运营可见
K5 证据可外锚
```

只过兼容门，版本号只能叫 2.5。  
3.0 不发布一个“只有内部结构变了”的版本。

**理由**

- 重写本身不产生用户价值。
- 2.0 已经能用；3.0 必须解决 2.0 做不到的事。
- 先定跨越门，才能防止重写退化成“把旧代码搬一遍”。

**代价**

- 3.0.0 范围变大，可能推迟。
- 新增工具和页面增加测试面。
- 需要为 K1-K5 各写验收，不能只写“已完成”。
