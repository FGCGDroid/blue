# 蓝队插件 3.0 立项书

> 状态：M0 契约、M1 骨架、M2 数据层、M3 路径阻断、M3.5 响应执行/外锚已完成（107 个 JS）
> 开工状态：已开工（2026-11-17）
> 立项日期：2026-11-17
> 代码状态：8 个 repo、迁移/回滚、路径/策略/独立网关/指标、manual/mock 执行器、file/https 外锚可运行；工具、UI、证据包仍占位
> 维护线：2.0 继续维护，只修 P0、安全和 DSH 兼容
> 作者仍在维护本项目；本文是开发计划，不是交接声明。

## 一句话

3.0 不是把 2.0 重写一遍。  
3.0 是 2.0 的能力超集：保留现有 66 个工具和数据，同时把“检测、台账、建议”推进到“可阻断、可测试、可执行、可运营、可外证”。

兼容是地板，不是天花板。

## 为什么立项

2.0 已经可用，但结构债集中在四处：

| 位置 | 规模 | 问题 |
| --- | --- | --- |
| `lib/tools.js` | 2609 行 | 66 个工具、参数校验、业务逻辑、SQL 混在一起 |
| `lib/client.js` | 1797 行 | 控制台单体，状态分散，页签之间靠全局变量 |
| `lib/store.js` | 1384 行 | 建表、迁移、领域状态机混在一起 |
| `lib/gateway.js` + `lib/inline-guard.js` | 335 行 | 先读 body 再检查，路径用正则，无法保证阻断 |

继续在 2.0 上打补丁，只会让这四处更厚。  
但只把这四处拆开也不够：那只是“更整齐的 2.0”。3.0 必须同时完成结构重写和能力跨越。

## 目标

3.0 要同时做到：

```text
1. 路径阻断可证明：先规范化、再策略判定、最后才读 body
2. 依赖方向可检查：domain 不依赖 infra/tools
3. 现有 66 个工具行为不变：名称、参数、返回、错误码保持兼容
4. 旧数据可迁移：2.0 SQLite 能迁到 3.0，且能回滚
5. 高风险动作仍走审批：pending_approval 语义不退化
6. 证据链不退化：timeline 哈希、Ed25519 签名、锚定保持
7. 控制台可替换：Host API 先稳定，UI 后重写
8. 至少 5 项 2.0 做不到的能力，且每项有验收
```

## 3.0 跨越门

以下 5 项是 3.0.0 的硬门槛。只满足兼容、不满足跨越，只能叫 2.5，不能叫 3.0。

### K1 真阻断

```text
2.0：网关是可选的，路径规则基于正则，检测到异常不一定阻断
3.0：策略判定在 body 读取之前，block 直接返回
验收：40 条路径向量全绿；canary 上游 hit_count=0；决策日志可追溯
```

### K2 策略可测试

```text
2.0：路径规则写死在代码里，改规则要改代码
3.0：策略文件版本化，可 validate / test / diff / reload
验收：不改代码能新增保护前缀；错误策略拒绝加载；旧策略可回滚
```

### K3 受控响应可执行

```text
2.0：只生成响应计划和待审批任务，执行靠人
3.0：受控执行器，dry-run 先行，审批后才执行，执行后验证，失败可回滚
验收：没有审批不能执行；dry-run 不产生副作用；回滚有证据
```

默认适配器是 `manual`，只打印命令，不自动执行。  
真实 `iptables` / `nft` / `fail2ban` / 删除 / 杀进程仍不在 3.0.0 自动执行范围内。

### K4 运营可见

```text
2.0：只有 JSONL 日志和页面统计
3.0：网关 /metrics、/healthz、每规则命中计数、上游错误计数
验收：Prometheus 文本可抓取；端口占用/策略非法/上游异常能看出
```

### K5 证据可外锚

```text
2.0：锚点只在本地 SQLite
3.0：锚点可推到外部 sink（文件 / HTTPS webhook），并可验证
验收：本地库被重算也过不了外部锚点；sink 失败不阻塞主流程
```

控制台的跨越放到 3.1：策略中心、网关面板、响应执行时间线。

## 非目标

3.0 开发期不做：

```text
不为加工具而加工具；只加跨越所需的工具
不重写控制台（3.1 再做）
不自动执行真实 iptables / nft / fail2ban / 删除 / 杀进程
不做多级审批流
不引入运行时 npm 依赖
不改变现有 66 个工具的名称、参数名、返回结构
不把 high 风险任务改成自动派发
```

## 原则

```text
1. 全量重写实现，不全量推翻契约
2. 先判定，后读 body
3. 解析失败一律 fail-closed
4. 依赖方向必须能被脚本检查
5. 旧模块不删，直到对应 parity 全绿
6. 3.0 开发期 2.0 冻结
7. 零新增运行时依赖
8. 每个里程碑结束必须能跑、能演示
9. 兼容是地板，不是天花板
10. 每项跨越必须有验收，不能靠“感觉更强”
```

## 质量门

3.0.0 发布前必须同时过两门。

兼容门：

```text
1. 现有 66 个工具 parity 全绿
2. 任务状态迁移矩阵全绿
3. 2.0 数据迁移与回滚演练通过
4. 影子双跑零决策分歧
5. 2.0 运行红线逐条有回归测试
```

跨越门：

```text
K1 真阻断：路径向量 40 条全绿，canary 命中 0
K2 策略可测试：不改代码能改策略，错误策略拒绝加载
K3 受控响应：dry-run 无副作用，无审批不能执行，可回滚
K4 运营可见：/metrics 与 /healthz 可用，规则计数可查
K5 证据外锚：外部 sink 可验证，sink 失败不阻塞主流程
```

只过兼容门，叫 2.5；两门都过，才叫 3.0。

## 风险

| 风险 | 缓解 |
| --- | --- |
| 全量重写导致行为漂移 | M0 固定向量 + M4 parity + M4.5 影子双跑 |
| 2.0 维护吃掉 3.0 时间 | 2.0 冻结，只修 P0；每周固定 2 小时 |
| 数据迁移不可逆 | 迁移前备份，版本门，回滚脚本 |
| 路径阻断漏绕过 | 40 条对抗向量，canary 命中为 0，fail-closed |
| 跨越门导致范围膨胀 | K1-K5 固定；新增需求一律进 3.2 |
| 项目无限期 | 每个里程碑可演示；3.0.0 不因 UI 未重写而推迟 |
| 单人疲劳 | 每 8 周留 1 周缓冲，不排开发 |
